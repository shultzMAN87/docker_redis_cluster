# Redis Cluster

Учебный стенд: кластер Redis из шести нод (3 мастера + 3 реплики) в Docker,
доступный с хоста обычным клиентом Redis — без кластерной библиотеки.

Пространство ключей режется на 16384 слота и распределяется между мастерами.
Это единственный механизм в Redis, дающий рост ёмкости и пропускной способности
на запись. Перед кластером стоит Envoy: он держит у себя топологию и сам
отрабатывает редиректы, поэтому снаружи шесть нод выглядят как один Redis.

> Если задача — не «разложить данные по нодам», а «пережить падение ноды без
> простоя», нужен не кластер, а Sentinel. См. [Cluster или
> Sentinel](#cluster-или-sentinel) и проект `15_RedisSentinel`.

---

## Состав стенда

| Сервис | Порт хоста | Роль |
|---|---|---|
| `redis-node-1` … `redis-node-6` | 7000–7005 | ноды кластера |
| `envoy` | 6379, 9901 | cluster-aware прокси, точка входа для данных |
| `cluster-init` | — | одноразовая сборка кластера |
| `redisinsight` | 5540 | веб-интерфейс |
| `client` | — | Python-песочница (по профилю) |

Имя сервиса и порт смещены на единицу: `redis-node-1` слушает 7000. Так
сложилось исторически; соответствие зафиксировано в таблице и в
`scripts/common.py`.

Кто из шести нод станет мастером, решает `redis-cli --cluster create` при
сборке, и раскладка меняется от запуска к запуску. Полагаться на порядок не
стоит — смотрите `python scripts/cluster_info.py`.

## Быстрый старт

```bash
docker compose up -d
docker compose logs cluster-init
```

Никакой настройки перед запуском не нужно: стенд не зависит ни от адреса
машины, ни от сети. Ожидаемый финал в логах — `cluster_state:ok`,
`cluster_known_nodes:6`, `cluster_size:3`.

Проверка:

```bash
pip install -r requirements.txt
python scripts/cluster_info.py
```

Работа с данными обычным `redis-cli`, если он есть на хосте:

```bash
redis-cli -p 6379 set foo bar
redis-cli -p 6379 get foo
```

Обратите внимание: без флага `-c`. Он здесь не нужен — редиректы обрабатывает
Envoy, а не клиент.

## Две точки входа, и это важно

У стенда сознательно два способа обращения, с разным назначением.

**Порт 6379 (Envoy) — для данных.** Обычный клиент Redis, никакой кластерной
библиотеки. Envoy опрашивает `CLUSTER SLOTS`, держит топологию у себя,
перехватывает `MOVED` и `ASK` и переспрашивает нужную ноду сам. Клиент видит
одиночный Redis.

**Порты 7000–7005 (ноды напрямую) — для диагностики.** `CLUSTER INFO`,
`CLUSTER NODES`, `CLUSTER KEYSLOT`, `DBSIZE`, `INFO` выполняет сама нода,
редиректы для них не нужны, поэтому с хоста они работают.

Чего делать нельзя: обращаться к ноде напрямую за чужим ключом. Ответ `MOVED
12182 172.18.0.4:7002` укажет на внутренний адрес docker-сети, недостижимый с
хоста. Это не поломка, а прямое следствие архитектуры — см. ниже.

## Как работать с данными

### Из командной строки

Если `redis-cli` установлен на хосте:

```bash
redis-cli -p 6379 set user:1 Иван
redis-cli -p 6379 get user:1
redis-cli -p 6379 del user:1
```

Если не установлен — тот же `redis-cli` есть в любом контейнере ноды:

```bash
docker compose exec redis-node-1 redis-cli -h envoy -p 6379 set user:1 Иван
docker compose exec redis-node-1 redis-cli -h envoy -p 6379 get user:1
```

Флаг `-c` не нужен ни в одном из случаев: редиректы обрабатывает Envoy.

### Из Python

Обычный клиент, без кластерной библиотеки:

```python
from redis import Redis

client = Redis(host="127.0.0.1", port=6379, decode_responses=True)

client.set("user:1", "Иван")
print(client.get("user:1"))

# Ключи с общим hash tag лежат в одном слоте - для них доступно всё,
# включая транзакции и Lua.
client.mset({"{user:1}:name": "Иван", "{user:1}:email": "ivan@example.com"})
print(client.mget(["{user:1}:name", "{user:1}:email"]))
```

Полный пример — `app/main.py`.

### Что работает и что нет

| Операция | Через Envoy (6379) | Напрямую к ноде (7000-7005) |
|---|---|---|
| `GET`, `SET`, `DEL` по одному ключу | да | только для своих слотов |
| `MGET`, `MSET` в разных слотах | да, Envoy разобьёт по нодам | `CROSSSLOT` |
| `MULTI`/`EXEC` в разных слотах | нет | нет |
| `MULTI`/`EXEC` с общим hash tag | да | да, на нужной ноде |
| `CLUSTER INFO`, `CLUSTER NODES` | нет | да |
| `DBSIZE`, `INFO`, `CLUSTER KEYSLOT` | нет | да |

### Ловушка: pipeline по умолчанию транзакционный

В redis-py `client.pipeline()` без аргументов оборачивает команды в
`MULTI`/`EXEC`. Если ключи попадут в разные слоты, вы получите
`ClusterCrossSlotError` — даже через Envoy, потому что прокси не может
разложить транзакцию по нодам.

```python
# Упадёт: MULTI по ключам из разных слотов
pipe = client.pipeline()

# Работает: пакетная отправка без транзакции
pipe = client.pipeline(transaction=False)
```

Транзакция допустима только тогда, когда все ключи в ней имеют общий hash tag.

### Переменные окружения

Стенду они не нужны, но скрипты их понимают:

| Переменная | По умолчанию | Зачем |
|---|---|---|
| `REDIS_LAB_HOST` | `127.0.0.1` | адрес, где опубликованы порты; менять, только если Docker на удалённой машине |
| `REDIS_LAB_PORT` | `6379` | порт Envoy, используется в `app/main.py` |

## Почему ноды объявляют внутренние адреса

Ранние версии этого стенда заставляли ноды объявлять IP хоста
(`cluster-announce-ip`), чтобы кластер работал с хоста напрямую. Доступ это
давало, но ценой, которая обнаружилась не сразу: announce-адрес используют не
только клиенты, но и сами ноды — для шины gossip и для репликации. Весь
внутрикластерный трафик уходил из контейнера на хост, через docker-proxy и
обратно в соседний контейнер.

На Docker Desktop под Windows эта петля оказалась ненадёжной, и проявлялось это
двумя способами:

- **Пакет `CLUSTER MEET` терялся.** Он отправляется однократно, повторов нет.
  Не дошёл — нода навсегда остаётся в одиночестве, а `redis-cli --cluster
  create` бесконечно ждёт её на `Waiting for the cluster to join`.
- **Полная пересинхронизация вставала.** После каждого failover вернувшаяся
  нода начинала тянуть снапшот с мастера, зависала на этом и переставала
  отвечать даже на `PING` — при том, что порт был открыт.

Второе не лечилось ничем: ни отключением RDB-канала
(`repl-rdb-channel no`), ни отключением diskless-синхронизации
(`repl-diskless-sync no`). Дело было в самой петле, а не в способе передачи.

Поэтому ноды вернулись к адресам docker-сети — шина и репликация целиком внутри
и работают штатно, — а доступ с хоста дал Envoy. Побочный выигрыш: стенд
перестал зависеть от IP машины. Сменили сеть, включили VPN, перенесли проект на
другой компьютер — ничего править не нужно.

## Демонстрации

Скрипты запускаются с хоста из корня проекта и убирают за собой ключи.

### Шардирование

```bash
python scripts/demo_sharding.py
```

Показывает расчёт слота от имени ключа, распределение 1000 ключей по трём
мастерам и hash tags. Отдельно — контраст: один и тот же межслотовый `MGET`
нода отвергает с ошибкой, а Envoy выполняет, разбив по нодам. Со стороны это
выглядит как «прокси снял ограничение», но атомарности в таком запросе нет, и
скрипт объясняет, почему.

### Failover

```bash
python scripts/demo_failover.py
```

Останавливает мастер, дожидается промоушена реплики и проверяет данные **тем же
клиентским соединением** — оно не переподключается и о смене мастера не знает,
топологию обновляет Envoy. Затем возвращает ноду и убеждается, что она
действительно отвечает на `PING`, а не просто «контейнер запущен». Около минуты.

### Состояние кластера

```bash
python scripts/cluster_info.py
```

## RedisInsight

Откройте <http://localhost:5540> и добавьте базу. Два варианта, оба рабочие:

**Как кластер** — контейнер RedisInsight находится в docker-сети, поэтому
внутренние адреса ему доступны:

- **Host:** `redis-node-1`, **Port:** `7000`
- кластерный режим определится автоматически по `CLUSTER INFO`

**Как одиночный Redis через Envoy:**

- **Host:** `envoy`, **Port:** `6379`

Первый вариант показывает реальную структуру кластера и распределение слотов —
для учебного стенда он интереснее.

Кнопку **Test Connection** в актуальных сборках лучше не трогать, она может
возвращать 404; жмите сразу **Add Redis Database**.

## Ограничения кластера

Ключи лежат на разных нодах, поэтому операция над несколькими ключами работает,
только если все они в одном слоте:

- `MSET`, `MGET`, `SUNION`, `SINTER`, `RENAME` — иначе `CROSSSLOT`;
- транзакции `MULTI`/`EXEC` — только внутри одного слота;
- Lua-скрипты — все `KEYS[]` в одном слоте;
- нет `SELECT`, доступна только база 0;
- `KEYS`, `SCAN`, `DBSIZE` возвращают данные только той ноды, к которой вы
  обратились.

Обходится hash tags: часть имени в фигурных скобках берётся для расчёта слота,
поэтому `{user:100}:name` и `{user:100}:orders` лягут вместе. Схему именования
приходится проектировать заранее — главная причина, по которой перевод готового
приложения на кластер редко бывает бесплатным.

Envoy часть этих ограничений маскирует, разбивая мультиключевые запросы по
нодам. Удобно, но атомарности это не даёт: получается несколько независимых
запросов, между которыми данные могли измениться. Транзакция через границу
слотов невозможна ни с прокси, ни без него.

Отдельно: если умрут и мастер, и его единственная реплика, диапазон слотов
останется без хозяина, и по умолчанию (`cluster-require-full-coverage yes`)
**весь кластер** перестанет обслуживать запросы.

## Cluster или Sentinel

| | Cluster (этот проект) | Sentinel (`15_RedisSentinel`) |
|---|---|---|
| Что делает | делит данные между мастерами | дублирует данные на реплики |
| Ёмкость | сумма всех мастеров | RAM одной ноды |
| Масштабирование записи | да | нет |
| Полный набор команд | нет, ограничения по слотам | да |
| Клиент | cluster-aware либо прокси | обычный + discovery через sentinel |
| Кто выполняет failover | сами ноды по gossip | внешние процессы-наблюдатели |
| Минимум для отказоустойчивости | 6 нод | 2 ноды с данными + 3 sentinel |

Короткое правило: **если данные помещаются в одну ноду, кластер не нужен** — это
и официальная рекомендация Redis. Кеш приложения, хранилище сессий,
распределённые блокировки почти всегда укладываются в память одной машины, и
задача там звучит как «не лечь при отказе», а не «масштабировать». Это область
Sentinel.

Кластер оправдан, когда упёрлись в физику одной машины: активных данных больше,
чем RAM самого крупного доступного сервера, или поток записи превышает то, что
переваривает один мастер.

## Как проверить, что стенд исправен

Полная приёмка с чистого листа. Занимает около трёх минут.

```bash
docker compose down
docker compose up -d
docker compose logs cluster-init
python scripts/cluster_info.py
python scripts/demo_sharding.py
python scripts/demo_failover.py
python scripts/demo_failover.py
python app/main.py
docker compose ps
```

На что смотреть:

1. **`cluster-init`** — собрал с первой попытки. Строки «В кластере не хватает
   нод» или «Назначаю реплики» означают, что сработал аварийный ремонт: не
   ошибка, но повод присмотреться. Финал — `cluster_state:ok`,
   `cluster_known_nodes:6`, `cluster_size:3`.
2. **`cluster_info.py`** — шесть нод, три мастера со слотами, три реплики.
3. **`demo_sharding.py`** — все шесть шагов до конца. Ключи распределены
   примерно по трети на мастера (разброс в пределах 300–370 — норма).
4. **`demo_failover.py` дважды** — оба раза нода возвращается, отвечает на
   `PING` и становится репликой нового мастера. Потеря нескольких ключей из
   200 штатна: репликация асинхронная.
5. **`app/main.py`** — отработал обычным клиентом, без `RedisCluster`.
6. **`docker compose ps`** — все контейнеры `healthy`. Только что
   перезапущенная нода может быть в `health: starting` секунд двадцать.

Отдельно — настоящий кластерный клиент изнутри сети:

```bash
docker compose --profile client up -d
docker compose exec client python /app/main_native.py
```

Должен показать список мастеров по внутренним адресам и отказ на межслотовом
`MGET`. Это контраст с `app/main.py`, который через прокси того же ограничения
не видит.

## Управление стендом

```bash
docker compose up -d              # поднять
docker compose ps                 # статус и healthcheck
docker compose logs cluster-init  # как прошла сборка кластера
docker compose down               # остановить
docker compose down -v            # остановить и стереть данные RedisInsight
```

Персистентность отключена намеренно (`appendonly no`, `save ""`): стенд
эфемерный, каждый `up` даёт чистый предсказуемый кластер.

Сборка идемпотентна и проверяет результат по-настоящему: шесть нод, три мастера
со слотами, три реплики. Одного `cluster_state:ok` недостаточно — он бывает `ok`
и у наполовину собранного кластера. Если состав не сошёлся, скрипт добивает
недостающие ноды через `CLUSTER MEET`, назначает реплики, а при неудаче
сбрасывает состояние и пробует заново, до трёх раз.

## Диагностика

**Стенд не поднялся, `cluster-init` завершился с ошибкой.** Смотрите
`docker compose logs cluster-init`: там видно, на каком шаге остановилось.

**`redis-cli -p 7000 get somekey` возвращает `MOVED` на адрес 172.x.x.x.**
Штатное поведение. Прямое обращение к ноде годится только для диагностических
команд; за данными идите на порт 6379.

**Клиент на 6379 не подключается.** Проверьте готовность прокси:
`curl http://localhost:9901/ready`. Статистика — на
`http://localhost:9901/stats?filter=redis`.

**Одна нода `unhealthy`.** Кластер может продолжать работать, если выпала
реплика. Посмотрите `docker compose ps` и `python scripts/cluster_info.py`.
Поднять: `docker compose down` и затем `docker compose up -d` — именно `down`,
а не `restart`, потому что `restart` не пересоздаёт контейнер.

**`CROSSSLOT Keys in request don't hash to the same slot`.** Штатное поведение
кластера при прямом обращении к ноде. Используйте hash tags — см.
`scripts/demo_sharding.py`.

**`ClusterCrossSlotError: Keys in request don't hash to the same slot` при
использовании pipeline.** `client.pipeline()` в redis-py транзакционный по
умолчанию. Возьмите `client.pipeline(transaction=False)` или дайте ключам общий
hash tag — см. [Как работать с данными](#как-работать-с-данными).

**Ошибка вида `caused error: 14522 172.18.0.5:7002`.** Это редирект `MOVED` с
отрезанным префиксом: сначала номер слота, затем нода-владелец. Envoy не может
перенаправить команду внутри `MULTI` и отдаёт ошибку клиенту как есть. Причина
та же — транзакция через границу слотов.

**Скрипты падают на Windows с `no such file or directory`.** Признак того, что
`create-cluster.sh` сохранён с CRLF. В проекте есть `.gitattributes`, который
держит LF.

## Безопасность

Стенд предназначен **только для локальной разработки и обучения**:

- аутентификация не настроена, пароля нет;
- `protected-mode no` на всех нодах;
- Envoy принимает соединения без ограничений;
- расширение `envoy.clusters.redis` не является hardened и рассчитано на
  доверенное окружение с обеих сторон.

Не выставляйте стенд в интернет.
